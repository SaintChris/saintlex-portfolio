Production pilot

IREE Staff Assistant and Website Chat

A staff assistant over 32 product documents and a public website chat, with rate limits, prompt-injection guards and a question set I rerun after every change.

Read the case study

Problem

Staff answer a lot of product questions: inverter limits, battery specs, warranty terms. The answers sit in dozens of manufacturer datasheets and manuals. A public chatbot that guesses about prices or warranties would cause more trouble than it saves.

What I built

Two assistants on one small server. The staff assistant answers from 32 product documents, combining keyword and meaning-based search with a reranker. The website chat answers only from reviewed public facts: every answer cites an approved page, or the visitor is referred to the team. Guards block obvious prompt-injection attempts and replace any reply that quotes a price or repeats the hidden rules. The gateway keeps no transcripts or IP addresses.

A fixed set of real product questions (51 at last count) is rerun after every change. When a different embedding model dropped the score, I reverted it.

Stack

Open WebUI, Node.js gateway, Python, Docker Compose, Caddy, Cloudflare Access and Tunnel, ChromaDB, BM25 hybrid search with a cross-encoder reranker, GitHub Actions, Dependabot, Trivy, restic, a hosted LLM.

My role

I designed, built and run all of it. I use AI coding agents for much of the code, and I review and test their changes before they ship.

Status

The staff assistant runs as a pilot on the company server. The website chat is built into the redesigned company website, which is waiting on launch approval. Next: a table-aware document extractor.

IREE Solar Website Redesign

A 15-page Squarespace redesign built from Git source, checked at seven screen widths, and verified against the saved site after every save.

Read the case study

Problem

The website needed to explain solar, battery and water services clearly and send each enquiry to the right form. It had to stay on Squarespace so the team can keep editing it, and every claim had to be one the company had approved.

What I built

A redesign of 15 pages, plus site-wide styles and scripts for all 20 pages. The custom code is built from one Git repository; after each save I read the page back and compare it with the build. Motion and layout live in CSS with reduced-motion fallbacks. The interactive parts are small: FAQ search, a keyboard-friendly project gallery, and a guided enquiry path that pre-fills the right form. A later code review found two bugs on the saved site, which I fixed and covered with regression checks.

Stack

Squarespace 7.1, Tailwind CSS, TypeScript, Vite, JavaScript, Git and GitHub, Google Sheets, browser-based layout and interaction checks.

My role

I wrote the redesign spec from the manager's notes, built the source, saved and verified every page, and applied the approved copy. AI coding agents did much of the implementation under my direction.

Status

Complete and password-protected while it waits for launch approval. Before launch: end-to-end form tests, real-phone checks and redirects from the old pages.

Professional work

Solar and Battery Performance Reporting

Customer and internal PDF reports from Tesla Powerhub data, with a read-only collector and strict rules about what the data can and can't show.

Read the case study

Problem

Customers and the service team ask questions like "why is my battery charging from the grid?" The answers are in each system's monitoring portal, but reading them by hand takes time, and a reporting gap is easy to mistake for an equipment fault.

What I built

A repeatable process that turns one site and one date range into two PDF reports. A read-only script in my signed-in portal session pulls daily energy totals, 15-minute power data, one-minute grid status, battery charge, alerts and settings. Daily figures must add up to the period totals before use, and outages come from the grid status, not from gaps. Every number comes from the collected data, with no estimates of system size, tariffs or savings.

Before this I built an operations dashboard prototype that runs only on simulated telemetry. Missing or stale data is never shown as healthy.

Stack

Tesla Powerhub, JavaScript, Python, ReportLab, matplotlib, JSON, Google Drive.

My role

I built the collector, the report layouts and the findings rules, and I write and check each report. Reports go out only after review.

Status

Used for a few customer sites. When API access is issued, collection switches to the official API; each query is already mapped to its endpoint.

AI-Assisted Engineering Workstation

My setup for working with AI coding agents: local memory, a task API, nightly upkeep and guard rails on risky commands.

Read the case study

Problem

I do most of my building with AI coding agents (Claude Code and Codex). Out of the box they forget context between sessions and can run destructive commands without warning, and my notes, tasks and code kept drifting into duplicate copies.

What I built

Notes live in an Obsidian vault, tasks in Super Productivity, code in Git. A small local service indexes the vault so agents can search past notes, read-only, and private folders are never indexed. A scheduled job rebuilds my priorities page and flags problems without moving or deleting anything. A patched Super Productivity build gives agents a local REST API for tasks. A mod holds risky shell commands until I approve them, and large jobs are split across worker agents in separate Git worktrees.

Stack

macOS, zsh, Python, TypeScript, SQLite full-text search, launchd, MCP, Claude Code, Codex, Obsidian, Super Productivity, Git and GitHub.

My role

I designed and built it for my own use. It's the environment I use for my day-to-day work.

Status

In daily use. One open issue: the command guard didn't fire in one long-running background session, though it worked in fresh ones, so I test any change to it in a new session.

04 / HOW I WORK

How I work

  1. 01

    Read before changing.

    Find out what the system does now and what still has to work after the change.

  2. 02

    Collect evidence.

    Logs, data and the actual error, not guesses. A reporting gap isn't an equipment fault.

  3. 03

    Make small changes I can undo.

    Take a restore point first. Keep secrets and customer data out of code, notes and logs.

  4. 04

    Check it the way a user would.

    Read the result back, run the tests, open it on the device.

  5. 05

    Write it down.

    What changed, why, and what's still open.

I use AI coding agents for a lot of my implementation work. I set the scope, review what they produce, and check the result myself before it ships.
